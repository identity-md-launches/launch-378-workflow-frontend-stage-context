# Event Checkin website (`lab-event-checkin`)

One static page for the EventCheckin Sepolia test toy: an organiser view (create, fund with an Approve step, close, reclaim, sign passes with `eth_signTypedData_v4`) and an attendee view (open or paste a pass, submit the check-in, withdraw rewards), plus every event's attendee list read from `CheckedIn` logs. Attendance records are not tickets or credentials.

Stack: Vite 7, React 19, TypeScript 5, viem 2. No backend, no indexer, no server rewrites: the export in `../dist/` works from any static host, an IPFS gateway subpath or an ENS name.

## Configuration: one file, read at runtime

`dist/imd-deployment.json` is the only source of contract addresses, chain id, ABI paths and public RPC URLs. The page fetches it on start, then fetches the ABI JSON files it references (`dist/abi/EventCheckin.json`, `dist/abi/LaunchToken.json`). There is no second address, chain or ABI map in the source.

The manifest is generated by `scripts/manifest.mjs` after every build from two verbatim copies of the workflow handoff:

| File | Purpose |
| --- | --- |
| `handoff/deployment.json` | Copy of `.imd/reads/deployment.json`: launch id, chain id, source commit, attestation hash, contract addresses, ABI hashes, deployment block |
| `handoff/network.json` | Copy of `.imd/reads/network.json`: the `network` block (RPC URLs, explorer, native currency, Uniswap v4 addresses) is copied unchanged into the manifest; `wallet_addEthereumChain` parameters are derived from that block at runtime |
| `public/abi/*.json` | Verbatim copies of `../docs/abi/*.json` at the pinned source commit; the manifest script fails if their canonical keccak256 differs from the handoff `abiHash` or if they differ from `docs/abi` |

Two values are baked in at build time from `handoff/deployment.json` through Vite `define`: the deployment block (start of log scans) and the launch id (the page refuses a manifest whose launch id differs from the one it was built for).

The page reads through the manifest's public RPC URLs in order (viem `fallback`), and signs only with the visitor's browser wallet. No private keys, API keys or WalletConnect project id are used or committed.

To point the site at another deployment, replace the two handoff files and the ABI copies, then rebuild. Do not edit `dist/imd-deployment.json` by hand.

### Optional WalletConnect

Browser-extension wallets are supported through EIP-6963 discovery with a `window.ethereum` fallback. No WalletConnect project id was supplied, so no WalletConnect connector is bundled. Adding one would mean installing a connector package, keeping the public project id next to the other configuration in `src/lib/config.ts`, and offering it as an extra entry in the wallet picker in `src/App.tsx`.

## Install, develop, preview, rebuild

Requires Node 20+ (built with Node 24.9) and npm.

```sh
cd web
npm ci                # exact versions from package-lock.json
npm run dev           # dev server; a Vite plugin serves a dev manifest built from handoff/
npm run typecheck     # tsc, strict, includes tests
npm run build         # tsc + vite build into ../dist + scripts/manifest.mjs
npm run manifest      # regenerate ../dist/imd-deployment.json only
npm run manifest:check
npm run preview       # serve ../dist locally (vite preview)
npm test              # vitest: unit + React integration tests with mocked RPC and wallet
```

`npm run build` always ends by rewriting `../dist/imd-deployment.json` with fresh SHA-256 hashes of every exported file (except the manifest itself). Commit `dist/` together with the source after any change; the publisher pins the committed files without rebuilding.

## Behaviour summary

- **Wallet and chain.** Connect, show the address with an explorer link, detect a wrong chain, offer `wallet_switchEthereumChain` and, on error 4902 or an equivalent message, `wallet_addEthereumChain` with parameters derived from the manifest's network block, then switch again. All transaction controls stay disabled until the wallet is on the configured chain and the page has verified that both addresses have code and that `EventCheckin.token()` equals the configured CHKN address.
- **Reads.** `eventCount`, `eventInfo` per event, `balanceOf`, `allowance(owner, EventCheckin)`, `withdrawable`, `attended`; refreshed after every mined transaction and every 20 s while the tab is visible. Attendee lists come from `CheckedIn` logs scanned in 5,000-block chunks from the deployment block, deduplicated by transaction hash and log index, with the last 64 blocks rescanned on each refresh.
- **Organiser.** Create (title UTF-8 encoded into bytes32, end time within 365 days, reward in CHKN), fund (step 1 `approve`, step 2 `fundEvent`, the live step is the filled button), close (with an inline confirmation), reclaim, and sign a pass. The signed payload is exactly the domain `{name: "EventCheckin", version: "1", chainId, verifyingContract}` and type `CheckIn(uint256 eventId,address attendee,uint256 deadline)`; the pass is shown as copyable JSON and as a `#pass?…` link.
- **Attendee.** A pass link or pasted pass is validated against the contract (event exists, not yet attended, event open, deadline not passed, then a dry-run `checkIn`) before the Submit control enables. The reward preview distinguishes recorded attendance from an awarded reward. Withdraw sends the caller's full credit.
- **Every transaction** is simulated first; revert reasons map to plain sentences (`src/lib/checkin.ts`); progress shows checking, wallet confirmation, pending and confirmed states with an explorer link.

## Validation

See `../docs/validation/frontend-validation.md` for the commands, outcomes, browser evidence, Better Interface review and the list of behaviour that was not exercised on the live chain. `npm test` covers typed-data exactness, pass parsing, revert-reason decoding, the switch/add-chain flow, log chunking and reorg handling, manifest validation and the React states (disconnected, no wallet, wrong chain, validation errors, pass link handling). The end-to-end run drives the built export in headless Chromium against an anvil fork of Sepolia with a mock wallet; its script is described in the validation record.
